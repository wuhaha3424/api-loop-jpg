带反馈回路的自动化流水线

经典工程模式（编译器 / CI 流水线同款）：数据正向流过六个处理阶段，每个阶段出口挂一个确定性校验器（独立脚本，判定不经过 LLM）；校验失败触发反馈回路送回重做，修不好走显式异常出口
LLM 在其中的角色是各阶段内的翻译器；流程走向和放行由确定性规则控制，不由 LLM 自主决定
📥 上游输入（Step 0 输入读取：三件套，缺一即停）
① 文本用例（TC 清单：操作步骤 + 预期结果） ② 测试分析定稿（字段级契约：断言字段对照表 / 判据规则 / 期望值常量 / 入参出参规格） ③ PRD/TRD 原文（预期结果的最终仲裁源）
正向数据流
校验失败回路
人工确认回路
异常出口
阶段 1

判据提取与判定

📥 输入：上游三件套全文
📤 输出：断言规格表（断言目标与判定.yaml）——每条 TC：字段路径 / 期望值 / 比对声明 / 数据需求，判据唯一权威源
自然语言 → 结构化断言规格。类比编译器前端：每个引用都要查到出处（三级证据链），LLM 只翻译不重解。
🚨 校验器 · 引用查证字段/期望值查无出处 → 拒绝编造，走异常出口记「待补」（本步查证靠纪律，产物在阶段 3 出口被后验闸对账）
阶段 2

物料先行

📥 输入：规格表的数据需求（目标字段+期望值）
📤 输出：测试数据集（每用例一份真实入参 + 试运行结论）
从线上日志取真实用户请求当测试数据（物料，即 fixture），不是手写模拟参数。每份先试运行一次，验证能否命中目标功能。
🚨 校验器 · 试运行验收命中不了目标功能 → 拒收换数据（回路①）；用户给的不豁免
阶段 3

接口用例生成

📥 输入：断言规格 + 已验收数据
📤 输出：可执行用例集（api-cases.yaml，唯一真相源——总览/底稿/上传清单全是它的视图）
把断言规格 + 验收数据组装成可执行用例集（含断言脚本）——字段和期望值都是上游查证过的，LLM 在这里是填空，不是自由创作。
🚨 校验器 · 生成物审查「声明的比对真的做了吗」静态审查，防假通过 → 不过打回（回路②）
阶段 4

执行

📥 输入：可执行用例集 + 测试数据集
📤 输出：执行报告（每用例三态结论 + 期望值 vs 实际值 + 可复现请求）
并发运行测试，输出结论和证据。类比跑单测，但被测环境是真实服务。
🚨 校验器 · 失败校准批量失败多是资料路径写错 → 探真实路径修正重跑，≤2 轮、只改取值不改标准
🚨 校验器 · 数据有效性执行发现数据无效 → 回阶段 2 补（回路③）
阶段 5

收口与渲染

📥 输入：执行报告逐条结论
📤 输出：用例执行总览（按原始用例粒度聚合）+ 转化底稿（100% 脚本渲染）
按原始用例粒度聚合总览；网页编辑器可视化查看、修改用例，改完重跑刷新报告；确认后渲染转化底稿。
🚦 门禁 · 人工确认没点确认一条不许回写；改了用例回阶段 4 重跑再来（回路④）
阶段 6

回写 DongTest

📥 输入：本地 PASS 用例 + 人工确认
📤 输出：平台用例资产 + 上传清单（唯一上传出口，防双传）
只回写本地跑通过的用例到测试平台（DongTest）：写后读验证 + 冒烟。
🚨 校验器 · 平台侧验证静态预检（时序/路径/冲突）+ 上传后回读 + 冒烟，失败修载荷重推（回路⑤）
① 试运行不命中 → 换数据重取
② 生成物不合格 → 回炉重生成
⑤ 平台验证失败 → 修载荷重推
③ 执行发现数据无效 → 回阶段 2 补数据、重新验收
④ 人工改用例 → 重跑阶段 4 → 再确认（可多轮，直到点头）
⏸异常出口 — 像编译器的告警通道
待补：引用查不到出处 → 显式记录「缺什么、找谁补」，绝不编造。上游资料补齐后重跑即可转化——跳过也要留痕。
降级：确实无法自动化（需 mock / 查库）→ 记录原因转人工，不静默丢弃。
🤖LLM 在这条流水线里的位置（在 / 不在）
在（做翻译）：阶段 1 自然语言→断言规格；阶段 3 规格+数据→可执行用例集；阶段 4 失败诊断（校准循环里探索真实字段路径）
不在（不碰决策）：流程控制——下一步做什么由编排脚本定义，不能跳步；通过标准——断言语义在阶段 1 锁定，之后只许改「怎么取值」不许改「什么算过」；放行——回写需要机器校验 + 人工确认双条件
✅正常出口 — 测试平台资产
放行三条件：本地执行 PASS ＋ 人工确认 ＋ 写后读验证——缺一不放行。
沉淀的是：跑通过的、断言不降级的、带可复现输入的长期回归资产。
🚨 校验器（闸）到底是什么 —— 每个阶段卡片上的 🚨 小方块，物理形态与触发机制
物理形态：独立脚本，不是 AI 判断 每个 🚨 背后是一个 Node.js 脚本（如 check-assertions.mjs）：读入阶段刚落盘的产物文件（YAML/JSON），用正则匹配 + 路径比对 + 计数做机械对账，输出退出码 0（通过）或 2（拦截）。全程不调用 LLM——判定标准写在脚本代码里，AI 执行时改不了。
怎么触发：编排层写死 → AI 执行 → 脚本裁决 不是定时器/git hook 自动触发。流程文档（SKILL.md）写死「该步出口必跑此脚本，不许绕过」→ AI 执行到该步用命令行跑 → 脚本独立解析产物给退出码。exit 2 时命令行必然返回错误，AI 读到错误明细，只能回炉重做——无法「假装通过」。
为什么必须挂在「阶段出口」 只有落盘后的产物文件（断言规格表、用例集、执行报告）才是稳定、可机械解析的对象；AI 过程中的「想法」挂不了闸。所以设计上强制每阶段先落盘、再过闸——闸永远检查的是文件，不是口头承诺。
为什么改不了闸：给闸上锁的闸 脚本放在只读目录（scenarios/），AI 想绕过得先改脚本——但所有写入请求先经过写保护钩子 guard-write.sh（exit 2 硬拦）。想绕闸 → 改闸 → 改闸被拦。另外每道闸都经「先红验证」：上线前拿已知有问题的旧产物跑，确认真能拦（实测首跑拦出 67 处）才启用。
📤 给下游的输出（每个产物都有明确消费者，无人消费的产物不生产）
执行报告 → 流程门禁本地执行报告是门禁查验项：有「未执行+原因」的降级留痕也认，但必须落盘。
上传清单 → 上传站哪些用例可上传的唯一权威表述；下游只认它，不从别处裸组包，防双传。
转化底稿 → 汇总站按 TC 逐条对账（ID 即关联键），汇总站按它聚合全端转化结论。
剩余输入 → 客户端站三件套原样传给下一个站点（task-testcase-app），处理端=客户端的用例归它。
可靠性的来源不是「LLM 很聪明」，而是确定性校验器 × 受控反馈回路 × 显式异常出口——LLM 的自由度只放在校验器能判对错的环节（翻译、生成、诊断）， 判不了对错的地方用 schema 约束 + 人工确认 兜底。每个回路都有终止条件（校准 ≤2 轮、确认必须人点头），不会死循环，更不会静默绕过。
